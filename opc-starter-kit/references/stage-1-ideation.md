# 阶段一：想法阶段详细指导

> 本节是 skill.md §3.1 的详细展开，包含完整操作步骤、提问模板和判定规则。

---

## 阶段目标

验证问题真实存在、有足够的需求强度、差异化空间明确。

**核心问题："这问题值得做吗？"**

---

## 退出标准（绿队关卡）

在进入 MVP 阶段之前，以下条件必须全部满足：

1. **客户验证**：至少 5 次真实客户对话，且对话内容指向明确的需求存在
2. **竞品认知**：竞品格局分析完成，差异化空间被识别并有证据支撑
3. **趋势判断**：趋势分析完成，三个外部趋势已识别并评估
4. **原型验证**：轻量原型已通过 5 人试用，反馈支持继续
5. **红队通过**：红队关卡的三个维度反驳已被审阅，创始人能清晰且有逻辑地回应每一个论点

> 💡 注意：你永远不会有 100% 的确定性。退出标准的目的是让你有"足够的质性证据，让投入做 MVP 看起来是有理有据的决定，而不是一次信仰行动"。

## 微交付详细操作

### 步骤 1：打磨问题陈述

**产出**：`docs/problem-statement.md`

**操作流程**：

1. **触发**：用户说 `opc idea`（或 `opc 我有个想法`）或从仪表盘进入想法阶段
2. **第一步提问**（故事式）：
   - "跟我说说你的想法——不是你要做什么产品，而是你看到了什么让你觉得'这不对劲'的事？"
   - "最近一次你亲眼看到这个问题发生在谁身上？当时是什么情况？"
3. **反向提取**：听完用户的描述后，反向提取关键要素：
   - **谁**遇到了这个问题？（具体画像，不是"大家"）
   - **频率**如何？（每天/每周/每月？）
   - **严重度**如何？（影响收入？影响效率？影响情绪？）
   - **当前处理方式**是什么？（手动？用了竞品但不够？忍了？）
4. **转化为假设**：将上述信息转化为可测试的假设陈述：
   ```
   [目标用户] 每周花 [X] 小时处理 [问题]，
   因为现有方案 [局限]，他们当前的替代方案是 [当前做法]。
   如果有 [方案方向]，他们能省下 [量化收益]。
   ```
5. **进展摘要**：展示"进入前 vs 现在"的对比

**提问模板**：
```
✅ "最近一次你看到这个问题发生在谁身上？"
✅ "如果不解决这个问题，最严重的后果是什么？"
✅ "他们现在是怎么处理这个问题的？"
❌ "这个问题有多大市场？"
❌ "你确定这是个问题吗？"
```

---

### 步骤 2：竞品格局分析

**产出**：`docs/competitive-map.md`

**操作流程**：

1. **告知用户**：这是需要深度研究的任务，会创建子窗口任务文件
2. **创建任务文件**：`docs/task-competitive-analysis.md`，包含问题陈述和指示
3. **子窗口执行**：在新窗口执行四层竞品格局分析

**四层格局**：
- **第一层：直接竞品** — 解决完全相同问题的产品
- **第二层：间接竞品** — 解决同类问题但方式不同的产品
- **第三层：潜在收购方** — 可能收购你的公司
- **第四层：相邻玩家** — 当前不竞争但未来可能进入的玩家

**核心要求**：为每层的代表性竞品写出"为什么他们会赢"的论证——不是最容易反驳的版本，而是最强的版本。

**差异化验证**：
- 从竞品分析中提取你的差异化空间
- 验证这个空间是否真的"差异化"（竞品也能轻松进入吗？）
- 识别竞品的软肋（不是功能缺失，而是战略选择导致的不可覆盖的盲区）

---

### 步骤 3：趋势分析

**产出**：`docs/trend-analysis.md`

**操作流程**：
1. **外部趋势识别**：让用户思考三个可能在未来两年显著影响市场的外部趋势
   - 监管趋势：是否有新的法规正在讨论中？
   - 技术趋势：是否有新技术可能颠覆现有方案？
   - 人口/行为趋势：目标用户的构成或行为是否在变化？
2. **顺风/逆风判定**：对每个趋势，判断它是你假设的顺风还是逆风
3. **TAM/SAM/SOM 建模**：基于公开数据构建市场规模模型，压力测试背后的假设
4. **时机判断**：基于趋势分析，判断现在是进入的"正确时刻"吗？

**提问模板**：
```
✅ "如果两年后回头看，你觉得哪个外部变化最可能让这个市场变大或变小？"
✅ "有什么政策或法规正在讨论中，可能会影响你的目标用户？"
❌ "你觉得市场有多大？"
```

---

### 步骤 4：客户访谈引导（原步骤3）

**产出**：`docs/interview-guide.md`

**操作流程**：

1. **让用户先写**：让用户先写出他们想问的问题草稿
2. **审查四类问题**：
   - **诱导性问题**："你也会觉得手动报销很麻烦对吧？" → 修正为："你现在是怎么处理的？"
   - **面向未来的问题**："你会用这样的产品吗？" → 修正为："你上一次遇到这个问题时做了什么？"
   - **过宽的问题**："你觉得财务管理怎么样？" → 修正为："上周你花了多少时间在报销上？"
   - **社会期许问题**："你重视效率吗？" → 修正为："描述一下你最近一次处理这个问题的情况"
3. **为不同 persona 生成不同问题组**：如果用户识别了多个目标用户画像，为每个画像定制问题
4. **给出结构化的访谈引导文档**：包含开放阶段（建立信任）、探索阶段（深挖问题）、收尾阶段（确认理解）

---

### 步骤 5：访谈后合成（原步骤4）

**产出**：`docs/problem-hypothesis.md`

**操作流程**：

1. **引出故事**："跟我讲讲你和用户聊的情况——哪些和你预期一致？哪些让你意外？"
2. **追问具体**：对每个提到的用户，追问"他们当时怎么说的？""你当时怎么想的？"
3. **反向提取数据**：从故事中提取量化信息
4. **双清单对比**：
   - 清单A：支持假设的证据
   - 清单B：挑战假设的证据
5. **不对称检查**：如果清单A明显长于清单B，追问：
   > "这个不对称是数据本身就这样，还是你在访谈中有意无意地更关注了支持假设的信息？"
6. **问题陈述更新**：基于访谈结果，更新 `docs/problem-statement.md` 中的假设

---

### 步骤 6：轻量原型

**产出**：`docs/lightweight-prototype.md`

> 📌 这是想法阶段的最后一步。你还不是在造一个真实世界产品，而是在做一份功能样本，用于客户和投资人对话。

**操作流程**：
1. **定义核心交互**：你的方案依赖的那一个核心交互是什么？只做这一件事。
2. **搭建原型**：用最小的产品面把想法摆到真实的人面前。可以是交互式原型、功能演示或可点击的界面。
3. **5 人试用**：将原型放到 5 个来自已验证目标画像的人面前，请他们试用。
4. **记录反馈**：记录每次试用的反应——哪里让他们惊喜、哪里让他们困惑、哪里他们觉得"这对我没用"。
5. **决定方向**：基于 5 次试用反馈，判断是继续进入 MVP 还是回到画板。

**提问模板**：
```
✅ "如果只能做一件事来验证你的方案方向，那一件事是什么？"
✅ "试用后用户说的第一句话是什么？那是惊喜还是困惑？"
❌ "你觉得原型够不够好？"
```

**判定规则**：
- 5 人中 ≥ 3 人表示"这就是我需要的" → 进入 MVP
- 5 人中 ≥ 3 人困惑或表示不需要 → 回到问题陈述，重新审视假设
- 中间状态 → 与用户深入讨论后再决定

## 红队关卡（不可跳过）

**角色**："吝啬的投资人"

**输出三个维度的反驳**：

### 维度 A："这问题不值得做一家公司"
- 这是一个"功能"而不是一个"公司"
- 现有方案的替代成本很低
- 市场规模不足以支撑一个可持续的生意

### 维度 B："已有好方案，你的差异化不成立"
- 竞品已经覆盖了这个需求
- 你的差异化点是竞品一个sprint就能加的
- 用户切换的动力不足

### 维度 C："目标用户不会为此付费"
- 这个问题虽然烦人但不值钱
- 付费意愿和口头认可之间的差距
- 预算归属不清晰（谁出这笔钱？）

**每个维度至少 3 个有据论点。**

**执行方式**：
1. 先展示完整的红队论证
2. **不要立刻催促用户回应**——给ta沉默和思考的空间
3. 等用户自然反应后，再引导深度回应："你觉得哪个论点最有威胁？为什么？"

## 三角验证

在红队关卡前执行。要求用户从三个角度描述同一个问题：
1. 一个具体用户的故事
2. 一个数字（频率、影响范围）
3. 一个反例（有没有人说不需要？为什么？）

跨角度不一致的地方，就是确认偏误最可能藏身的地方。
